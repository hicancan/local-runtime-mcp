# Local Runtime MCP v15.0.0

Unified single-daemon runtime with three physically isolated surfaces, transparent
`stdio` thin-proxy attachment, and unified principal grants. All legacy overlapping
configuration paths (`models.key`, `capabilities.web`, `capabilities.native`) have
been removed cleanly.

## Three physically isolated surfaces

One running `lrmcp` daemon owns the machine's shared state (process sessions,
serialized filesystem commits, desktop UIA/input gate, browser extension bridge,
capability catalog with `.proposed/` approval loop, and model session pool) and
exposes three non-overlapping loopback listeners:

- **Local-only plane (`local`, default `127.0.0.1:9317`)**: never exposed through
  tunnels; rejects browser `Origin` headers, non-loopback `Host` headers, and
  reverse-proxy forwarding headers. Serves:
  - `GET /health`, `/mcp` (stateful Streamable HTTP with `LocalApps`), and
    `POST /mcp/attach` (full-duplex HTTP 101 stream for `stdio` thin proxies),
    authenticated by `local.token`.
  - `/v1/models`, `/v1/chat/completions`, `/v1/conversations/*`, and
    `GET /capabilities`, `POST /capabilities/invoke`, authenticated per client by
    scoped tokens in `grants.clients` (never `local.token`).
- **Browser extension bridge (`browser`, default `127.0.0.1:9315`)**: accepts only
  `chrome-extension://` origins with `browser.token`. Serves CDP execution,
  zero-secret webpage bridge `lrmcp.web.v1`, and the toolbar `L` owner panel.
- **Public / tunnel-facing gateway (`http`, default `127.0.0.1:9316`)**: serves
  remote `/mcp` (without `LocalApps`) and OAuth endpoints only. `/v1/*` model
  routes are no longer mounted on the public listener, and enabling `http.auth: oauth`
  for remote clients never interferes with local MCP clients.

## Transparent `stdio` thin proxy & `local` transport

- Run `lrmcp setup local` once to generate `local.token`.
- Run `lrmcp serve --transport local` for a local-only daemon, or
  `lrmcp serve --transport http --tunnel cloudflare --tunnel openai` to serve both
  local and remote clients from the same Host.
- Any local MCP client configured with `lrmcp serve --transport stdio` probes
  `127.0.0.1:9317/health` on startup. When a daemon is already running, `stdio`
  attaches as a stateless thin proxy over `/mcp/attach`—sharing the single browser
  bridge, desktop gate, process sessions, `LocalApps`, and live `tools/list_changed`
  notifications across multiple concurrent clients (e.g., multiple Codex instances).
  When no daemon is running, the first `stdio` instance hosts the local plane so
  subsequent `stdio` instances attach cleanly.

## Unified grants (`grants.web` & `grants.clients`)

- Website grants move from `capabilities.web` to `grants.web`.
- Local native clients (`studev-win`, `harness`, etc.) are first-class entries in
  `grants.clients`, created with `lrmcp setup client --id NAME --model ...`.
  Each client holds one independent scoped token on `127.0.0.1:9317` for both its
  granted `/v1/*` models (with isolated `client:<id>` conversation scope) and its
  granted read-only `/capabilities/*` tools, without borrowing a fake website grant.

## Breaking changes & migration

- Replace `capabilities.web` with `grants.web`.
- Replace `models.key` and `capabilities.native` with `grants.clients` entries
  (generated via `lrmcp setup client --id ...`) targeting `http://127.0.0.1:9317`.
- Replace `LOCAL_RUNTIME_MCP_MODEL_KEY` and `LOCAL_RUNTIME_MCP_NATIVE_CAPABILITY_KEY`
  with `LOCAL_RUNTIME_MCP_CLIENT_TOKEN` (for single-client configs) or
  `LOCAL_RUNTIME_MCP_CLIENT_TOKEN_<CLIENT_ID>`.
- Run `lrmcp setup local` to enable multi-client `stdio` sharing on `127.0.0.1:9317`.
- Run `lrmcp setup browser` and reload the browser extension so its version matches `15.0.0`.
